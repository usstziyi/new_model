run 指纹 ：不同 run 的 EEG 特征本身有系统性差异（电极接触、阻抗、放大设置、被试状态、疲劳、时间），所以“这个试次来自哪个 run”可以从特征里被识别出来。你的证据：run 身份解码 0.984 ，chance 0.022。

run–类别混杂 ：数据集设计让每个 run 内的句类分布高度不均（block 设计，一个 run 只覆盖部分句类），所以 run 身份和类别标签统计相关。你的证据：只用 run 猜句类就有 0.32 ，chance 0.10；每个 run 的多数类占比约 0.31 。

随机划分 让 train 和 test 共享同一个 run，于是模型可以通过“先认 run，再用 run 的类别分布”来猜类别。

所以更准确的说法是：

- 指纹是 可被利用的通道 ；
- 混杂是 让这个通道与标签相关的结构 ；
- 随机划分是 让训练和测试共享这个通道的协议缺陷 。

三者合起来，才造成 0.224 → 0.119 的下降。

- LORO：测试 run 的 R 没在训练中出现，模型只能依赖跨 run 稳定的 P ( Y ∣ X ) ；
- LODO：连“同一天”的相似性也被切断，只剩跨天稳定信息。


归因更清楚 ：你可以说“不是 EEG 里没有句义信息，而是 run 指纹 + run–类别混杂让随机划分高估了它”。

缓解手段不同 ：
- 针对 指纹 ：逐 run 标准化、对齐、对抗式 run-invariance；
- 针对 混杂 ：实验设计层面平衡每个 run 的句类分布，或在分析中对 run 做分层/加权；
- 针对 协议 ：LORO / LODO。

避免术语混淆 ：
- “data leakage”通常指 评估协议 问题（train/test 共享 run）；
- “confounding”指 数据生成结构 问题（run 与类别相关）；
- “fingerprint”指** nuisance 变量可学习**。
   建议在论文里把这三个词分别定义，否则审稿人会把它们当成同一件事。


随机试次划分在具有 run/session 结构的数据上会系统性高估句类解码性能；我们在本数据上量化了这一偏差，并证明它主要来自 run 指纹与 run–类别混杂；随后提出一种缓解方法，并在 LORO/LODO 协议下验证。

建议的三段式结构
1. 诊断（前半部分）
   - run 身份探针：run 几乎完全可解码（0.98），说明特征里有强 run 指纹；
   - run–类别混杂：只用 run 猜句类就有 0.32（chance 0.10）；
   - 随机划分 vs LORO vs LODO：0.224 → 0.119 → 0.095，量化“高于 chance 的优势”损失约 84%。
2. 归因（连接两半）
   - 说明随机划分的收益来自“同一 run 的试次同时出现在 train/test”，属于协议层面的泄漏；
   - 用 LORO/LODO 作为对照，把“句义解码”与“run/session 捷径”分开。
3. 缓解（后半部分）
   - 提出方法；
   - 必须用 LORO/LODO 评价 ，不能只看随机划分；
   - 同时报告“run 身份可解码性是否下降”和“句类跨 run/跨天准确率是否上升”，避免用“把 run 信息删掉、句类也一起删掉”换取表面提升。

run 身份高度可解码
run 与句类高度混杂
随机划分相对 LORO 明显虚高
跨天（LODO）基本回到 chance

尤其注意： “run 可解码”本身不等于“句类分类器用了 run” 。你现在有很强的间接证据（可解码 + 混杂 + 留出后下降），但最直接的证据是：在同一个深度模型上复现 random vs LORO 的落差，或者做 run-wise 归一化后看落差是否消失。

审稿人最可能追问的 6 件事
1. “只有线性模型和一套数据。” 建议至少补：
   - reading 任务（你已经有数据，命令现成）；
   - 一个代表性深度模型（仓库里已有 PMCNN/EEGNet 类实验）在 random / LORO / LODO 下的对照。
2. “run 身份高不代表句类分类器用了它。” 建议补：
   - 随机划分下每个 run 的准确率与“该 run 的多数类占比”的相关；
   - 或 run-wise 归一化后随机划分优势是否缩小。
3. “LORO 已经是常见做法，创新性在哪？” 需要明确贡献是“量化 + 缓解 + 协议”，而不只是“我们也做了 LORO”。
4. “LORO 还有一点高于 chance，你怎么解释？” 诚实报告：3/5 被试显著、2/5 不显著；LODO 后消失，说明残余可能来自日间相似性，而不是稳定句义。
5. “你的缓解方法是不是把类别信息也删了？” 必须同时报告：
   - run 身份准确率（应下降）；
   - 句类 LORO/LODO 准确率（应上升或至少不降）；
   - 随机划分准确率可以下降，这不是坏事。
6. “只有 5 个被试、单一数据集。” 至少在 limitation 里明确；有条件再加一个公开数据集或第二个任务。


缓解方法部分的硬性要求
- 评价协议 ：主表用 LORO 和 LODO；random split 只作为“诊断列”，不能作为方法优越性的主要证据。
- Baseline 必须包括 ：
  - 无缓解；
  - run-wise 标准化/归一化（最简单的强 baseline）；
  - 至少一种领域自适应/对抗式 run-invariance 方法；
  - 如果有，现成的 session alignment 方法。
- Negative control ：缓解后 run 身份准确率应显著下降；如果没降，说明方法没有真正去掉 run 信息。
- Ablation ：去掉方法各组件后的 LORO/LODO 准确率。
- 统计 ：5 被试的 mean±std、配对检验、CI；多重比较说明。


建议补的最小实验集
1. reading 任务跑同一套 random/LORO/LODO；
2. 一个深度模型复现 random vs LORO（证明不是线性模型特有）；
3. run-wise 归一化 baseline（证明简单方法能做到什么程度）；
4. 一张“既往工作 split 协议”审计表（数据集、任务、划分方式、报告准确率）；
5. 你的方法在 LORO/LODO 下的主结果与 run-identity 下降情况。

一句话： 论文结构可行，但要把“证明别人都错”改成“量化一类系统性风险”，并用深度模型复现、第二任务和 LORO/LODO 下的方法评估把故事补扎实。



所以合理的预期是： LORO 可能从 0.119 提升到 0.13–0.15，LODO 有机会略高于 chance。


值得试的方法（按成本从低到高）
1. 逐 run 标准化 / 重参考（必做 baseline）
对每个 run 的每个通道/频带做 z-score 或减去 run 均值，再训练分类器。

- 优点：几行代码，能去掉 run 级偏移；
- 注意：测试 run 的归一化使用了该 run 的无标签试次，属于 transductive，需要在方法里明确；
- 预期：LORO 可能小幅提升，LODO 不确定。

2. 去除 run 判别方向（正交化）
在训练集上拟合“run 分类器”，取其判别方向，把特征投影到与这些方向正交的子空间，再训练句类分类器。

- 可以只去掉前 k 个 run 判别成分；
- 同时报告“run 身份准确率下降”和“句类 LORO/LODO 准确率变化”；
- 风险：如果 run 与类别子空间高度重叠，会一起删掉句类信息。这个 trade-off 本身就是很好的论文图。

3. 领域自适应 / 对抗式 run-invariance
- 梯度反转（DANN）让表征无法预测 run；
- 或 IRM / group DRO，把 run 当作环境；
- 需要深度模型，成本较高，但比线性方法更有“方法论文”的说服力。

4. 测试时对齐（transductive）
用测试 run 的无标签试次估计其均值/协方差，做 CORAL 或欧氏对齐后再分类。

- 对 session drift 通常有效；
- 必须明确这是 transductive，不能和 inductive 结果混在一起。

5. 数据增强
跨 run mixup、通道 dropout、频带扰动等。

- 可能提升泛化，但未必真正去掉 run 指纹；
- 需要同时看 run 身份准确率是否下降。


指标	期望方向
run 身份准确率	下降（说明干扰被去掉）
LORO 句类准确率	上升，且跨被试一致
LODO 句类准确率	上升，至少稳定高于 chance
随机划分准确率	可以下降，这不是坏事


如果方法能把 LORO 稳定提升、并让 LODO 至少部分被试高于 chance ：故事成立，可以写成“诊断 + 缓解方法”。

如果 LODO 始终不动 ：不要硬说“恢复了真实解码”，把论文定位成 诊断/协议论文 更稳：量化随机划分的虚高，给出 run 探针 + 混杂诊断 + LORO/LODO 协议，方法部分作为“尝试与负结果分析”。负结果本身在方法学上是有价值的。

最容易被审稿人接受的组合是： protocol + 一个简单有效的 run-invariance 方法 + 深度模型复现 ，而不是只报一个线性模型上的提升。

句话： 缓解“混叠造成的虚高”肯定有方法；恢复“真实解码”要看数据里到底还有多少跨 run/跨天的稳定信号。以当前 LODO 的结果看，期望要保守，先把逐 run 标准化和 run 方向正交化这两个便宜实验做了，就能知道天花板大概在哪。


“负结果分析”指的是： 你认真试了缓解方法，用同一套严格协议评估，结果没有达到预期效果，然后把“没效果”这件事本身当作一个可解释、可复现的研究发现报告出来 ，而不是调参调到显著、或者把不利结果藏起来。

在你这篇论文里具体指什么
假设你试了这些缓解方法：

- 逐 run 标准化；
- 去除 run 判别方向（正交化）；
- 对抗式 run-invariance；
- 测试时对齐。

也就是： run 指纹确实被压下去了，但句类跨 run/跨天准确率没有提升，甚至下降 。这就是负结果——缓解方法没有“恢复真实解码”。

这样的负结果为什么有价值
1. 它支持你的诊断结论 ：不是“方法不够好”，而是“run 和句类信息高度纠缠，去掉 run 的同时也去掉了类别信号”，或者“跨天稳定信号本身就不存在”。
2. 它防止别人重复踩坑 ：告诉大家“简单去 run 不变性并不能恢复句义解码”。
3. 它给后续研究设定边界 ：如果连对抗式方法都无法提升 LODO，说明问题在数据/特征层面，而不是模型层面。
4. 它让论文更可信 ：审稿人通常更信任“报告了失败尝试”的作者，而不是只报成功的方法。

如果缓解方法有效：论文是“诊断 + 方法”。

如果始终无效：论文应定位为：

我们量化了随机划分的虚高，提出 run 探针 + 混杂诊断 + LORO/LODO 协议；并系统尝试了若干缓解方法，发现简单的 run-invariance 无法恢复跨天句类解码，说明瓶颈在数据/特征层面，而非模型层面。

这时 诊断和协议是主贡献，负结果是支撑性证据 。不要把整篇论文写成“我们试了一个方法，失败了”，否则容易被拒；要把负结果放在“为什么这个问题难以缓解”的讨论里。

一句话： 负结果分析 = 用严格协议证明“这条路走不通”，并解释为什么走不通；它本身不是失败，而是把失败转化为对问题本质的证据。
